## Ubuntu instalado em USB
A decisão da issue #29 está fechada: Ubuntu Server completo instalado no pendrive, com raiz ext4 e uma partição ext4 separada \`NIVUS_DATA\` para dados persistentes. O objetivo é iniciar outro computador x86_64 sem alterar o disco interno. Não é Casper Live.
O PR #34 foi integrado à `main` no commit `703efa4128f60460910b05ab344b60b082006a7e`. Todos os checks hospedados passaram no head `3a1621dc11d2532853ef83b9ab5ea47f64cfaca5`: seletor USB, seed/schema Subiquity, bootstrap pós-boot, integração ext4, smoke Compose, workflows gerais, índice e CodeQL. `deploy/portable_usb/install_nivus.sh` valida raiz e `NIVUS_DATA` no mesmo dispositivo USB, verifica ext4/rótulo/fstab/montagem e configura caminhos e guard persistentes antes de chamar o instalador Compose.
O fluxo continua usando a mídia oficial inicializável do Ubuntu e um seed NoCloud separado. A tela de armazenamento do Subiquity permanece interativa; a pessoa confere caminho, modelo, serial e capacidade antes de confirmar, porque o instalador apaga o USB escolhido. A primeira instalação do Compose precisa de Internet para instalar pacotes e construir/obter componentes. Depois de instalado, o Nivus local pode operar na LAN sem serviço de nuvem; inferência local e coordenação multi-nó são fases separadas.
Ainda faltam executar uma instalação real do Subiquity até o primeiro boot, instalar Nivus, autenticar no painel, reiniciar e verificar SQLite (`quick_check`), configurações, segredos e Docker persistidos, testar recuperação/rollback e fazer a matriz física UEFI/BIOS Intel/AMD. A CI hospedada e o loop ext4 validam software, não boot em USB físico nem compatibilidade universal. Consulte [deploy/portable_usb/README.md](../deploy/portable_usb/README.md) para o procedimento e seus limites.

## Regra automática do relé por bateria
O PR #50 integrou a regra solicitada: qualquer dispositivo móvel ativo e cadastrado que envie relatório autenticado, ordenado e com até 60 minutos de idade pode provocar somente `OFF` para o tópico fixo `nivus/edge/relay1` quando a bateria estiver em 20% ou menos. O código está incluído na release ativa `fff64a68f252f0b1290576e30b39ed78fbc15a7a`, mas falta cadastrar/configurar a fonte Home Assistant e validar a aceitação no broker e o relé físico. Há trava por ciclo baixo e limite de tentativas em falha do broker; leitura ausente, vencida, duplicada ou fora de ordem não provoca comando, e a recuperação da carga ou inicialização não envia `ON`. O token aleatório é mostrado uma vez e armazenado como SHA-256. A aceitação pelo broker não comprova a ação elétrica do relé.
## Registro e agente de nós (Fase 2)

A issue #65 foi concluída pelo PR #66 e o registro seguro consta na release ativa `fff64a68f252f0b1290576e30b39ed78fbc15a7a`. A API atribui IDs, aceita códigos de pareamento de uso único, guarda hashes de tokens, rotaciona sessões, ordena heartbeats e permite revogação.

O agente mínimo está implementado no PR #69, com checks de CI hospedada aprovados. Ele usa Python padrão, recusa HTTP, recebe o código sem eco no terminal, grava a credencial bearer em arquivo local `0600` dentro de diretório `0700`, renova sessão ao iniciar e envia apenas heartbeat com capacidades vazias. Retry tem limite; revogação encerra a conexão. O exemplo systemd usa usuário dedicado sem root. A credencial local é texto simples protegido por permissões do sistema; segredos não são criptografados nesse arquivo.

A CI do PR #69 cobre dois IDs separados, sessões, heartbeat, retry após rede indisponível, resposta perdida/replay, reinício do processo, arquivo de credenciais e revogação. Os testes invocam os handlers FastAPI reais com SQLite temporário por um transporte simulado em processo; isso não é um smoke HTTPS de ponta a ponta. Ainda faltam pareamento e execução em dois dispositivos independentes, validação real de certificado/TLS, instalação do unit, teste de reboot e cenário operacional de backup/restore. A entrega não agrega telemetria, executa comandos, controla MQTT, transfere arquivos ou atualiza nós.
